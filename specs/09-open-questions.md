# 09. Open Questions（未解決の判断事項）

実装着手前に決めるべき事項。各項目に推奨案を併記。

## 9.1 Q1: ポート番号

**問題**: バインドする固定ポート。

**選択肢**:
- A. `7000`
- B. `7700`
- C. `8765`
- D. ランダム（起動毎に変わる）

**推奨**: **B (`7700`)**。当初 A (`7000`) を採用したが、macOS の AirPlay Receiver (`ControlCenter` プロセス) が port 7000 を `*:7000` で wildcard bind しており、Tailscale IP 経由は問題ないものの `localhost:7000` / `127.0.0.1:7000` / `mac-studio.local:7000` で 403 を返してデバッグや PC からのテストが困難。`7700` は AirPlay と衝突せず、覚えやすさを維持。

**決定**: B — `7700` 固定（2026-05-06 改訂）。

**改訂履歴**:
- 2026-05-06: A → B（AirPlay 衝突を実機テストで検出、改訂）

## 9.4 Q4: ANSIエスケープのレンダリング深度

**問題**: Claude Codeの出力にはカラー・カーソル制御が含まれる。どこまで解釈するか。

**選択肢**:
- A. すべて`\x1b[...m`系をstripして表示（白黒）
- B. SGRカラー（30-37, 90-97）と太字のみ解釈
- C. xterm.jsを採用してフル解釈

**推奨**: **B**。可読性を保ちつつ実装軽量。xterm.jsは外部依存になるので避ける。プログレスバー等のカーソル制御はstrip。

**決定**: B — SGRカラー(30-37/90-97)と太字のみ解釈、カーソル制御はstrip。

## 9.13 Q13: cmuxとの関係（v1スコープ確定）

**問題**: 本人はmacOS上で [`manaflow-ai/cmux`](https://github.com/manaflow-ai/cmux)（Ghostty-based macOS terminal、AI coding agent向け）を日常使用している。CC Pocketとcmuxセッションを統合（Bridge）するか、独立運用するか。

**選択肢**:
- **A**. 独立運用（CC Pocketはtmux + `claude` CLIで別セッションを動かす）。Macではcmux、外出先ではCC Pocketで `claude --resume` 等で同workspaceを別プロセスで継続
- **B0**. cmux Socket APIに乗ってBridge（出力streaming APIが不在のためpollingか上流PR必要）
- **B1**. 入力のみcmux APIへ、出力は独自pane（二重管理で破綻、NG）

**調査結果**（cmux v0.64.2時点）:
- Socket: `/tmp/cmux.sock` (UDS, `CMUX_SOCKET_PATH`で上書き可)、JSON-line RPC
- 利用可能: `workspace.list/create/select/close`, `surface.split/list/focus/send_text/send_key`, `notification.create`, `sidebar.status/progress/log`, `ping/capabilities/identify`
- **不足**: 出力のリアルタイム購読 / 状態変化通知の購読がない（単発request/response設計）
- 認証: Off / cmuxプロセスのみ / allowAll の3モード、祖先プロセスチェック機構あり

**決定**: **A**（v1）。理由:
- B0はcmux仕様変更が前提でブロッカーが多い（output subscriptionの追加にcmuxメンテナの判断必要）
- A案は現在のSpec全章で実装可能
- v1で運用検証 → 「やはりcmuxセッションそのものをモバイル化したい」と1ヶ月以上欲し続けたらv2でB0再評価

**v2で再評価する条件**:
- cmuxに output subscription APIが追加された / 上流PR成立
- 自前で投資する時間が確保できる（fork or 別ターミナル自作）

## 9.14 Q14: サーバ停止中の出力をどうするか

**問題**: 現Specは`tmux pipe-pane`をCC Pocketサーバ起動時に発行する設計。サーバ停止中はpipeが止まり、`tmp/pipe/<windowId>.log`にも書かれない。「サーバ起動前から動いてた既存windowの出力」が見られない。

**選択肢**:
- **A**. tmuxの`pipe-pane`を永続化設定に（`~/.tmux.conf`に焼く、サーバ起動状態に非依存）
- **B**. サーバ起動時に`tmux capture-pane`でスクリーンバッファから現状取得して補完
- **C**. 仕様維持（サーバ停止中は記録なし、起動後の出力のみ追う）
- **A+B**. ハイブリッド（永続記録 + 起動時の現状補完）

**推奨**: **A+B**。Aで継続記録、Bで「サーバ起動前から動いてたwindow」もカバー。

**決定**: **A+B** — `~/.tmux.conf`に`pipe-pane`を永続記録設定として焼く + サーバ起動時に`tmux capture-pane`でスクリーンバッファから現状補完。
